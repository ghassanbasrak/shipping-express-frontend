# Ashamco Express migration conventions

Use `../bastaline-admin-frontend` as the reference for the new Fuse feature structure. Preserve existing Ashamco backend contracts and complete feature behavior. Reuse migrated shared components at their existing paths. Redux feature slices remain JavaScript (`*Slice.js`); pages, APIs, schemas, and entity models use TypeScript.

- An entity file such as `models/ICountry.ts` contains the root entity interface and exported interfaces for its nested domain objects (for example `IShipmentCountry`). Do not put form inputs, filters, pagination wrappers, request/response types, or unrelated entity interfaces there.
- Import reference entities from their own features. Pair reference IDs with populated fields: `countryId?: string; country?: ICountry;` and plural IDs with `countries?: ICountry[]`. Follow the backend's actual ID type. Migrate dependency entities/features before their consumers; ensure imports resolve. Do not claim a dependency feature is migrated when only its entity model exists.
- Keep `*Model.ts` focused on defaults and editable fields, following the reference. Put shared feature helpers in `Utils.ts`.
- Reuse validation helpers from `src/app/main/utils/validations.ts`. Use custom refinements such as `superRefine` for business rules. Preserve the source feature's required and optional fields.
- Follow reference `*Api.ts` structure: simple RTK Query endpoint definitions, request/response types declared in that file, and exported hooks. Avoid response normalization, generic PageResponse wrappers, transformResponse pipelines, and multi-request queryFn workflows. Keep any necessary multi-resource save orchestration in the feature's UI handlers and preserve recovery from partial saves.
- Follow reference detail pages: form methods and FormProvider in `Country.tsx`, a separate header, Tabs, and `country/tabs/BasicInfoTab.tsx`. Do not introduce a nested CountryForm component. Match reference FusePageCarded layout and header structure.
- Keep list pages such as `Countries.tsx` as simple FusePageCarded wrappers around their header and table. Put list initialization, filter selectors, queries, and pagination in the table as in the reference.
- Specify matching `flex` and `minWidth` for every table column, with `minWidth = flex * 100`. Boolean/tiny columns: 0.3/30. Codes, dates, numbers, statuses, enums: 0.5-0.7/50-70. Phone/email: 0.8-0.9/80-90. Names, notes, actions: 0.9-1.3/90-130.
- Define feature enum constants in `Utils.ts`, for example `transactionStatus = { pending: "pending", completed: "completed" }`. Export matching title and color helpers (`toTransactionStatusTitle`, `toTransactionStatusColor`) and reuse them throughout the feature. Follow the reference's translation keys and color conventions. Do not invent enums where none exist.
- Preserve unsaved form edits during background refetches and retain returned backend IDs so subsequent mapping saves update the same record.
- Salla, Odoo, product e-commerce, and comparison features have been removed. Keep packaging requests.

Validate affected behavior and run the active application typecheck/build. Full-source checks may include pre-existing unused template/shared-component issues; report their scope accurately.

List action visibility retains the source's administrator role check; direct detail access follows explicit view/update/delete grants. Related audit links are retained in admins-app/Utils.ts but are not shown until their owning operational features are migrated; enable them there as those routes become available. Permission identifiers for pending features do not imply those features have been migrated.

Do not count the welcome/sign-out `/home` page as the completed home/dashboard feature. Dormant source directories need an import audit before migration or retirement.

Refresh account details after successful submission without treating refresh failure as a failed creation. Verification requests retain all active document columns and tax/registration fields. Reversing approved/rejected verification decisions remains supported. Decision PATCHes contain status only, target the row's actual ID, require confirmation and invalidate list/account caches. Keep removal/bulk removal and verification creation unexposed because those controls were inactive in the source; onboarding verification submission stays in auth-app and invalidates the migrated review list.

Shared filter autocomplete must ignore automatic MUI reset input events when dispatching remote searches and must retain the chosen option label on selection. This prevents selected-account labels from overwriting typed searches. Both request features keep Excel worksheet-compatible export names (at most 31 characters); verify downloaded workbook content with filters applied.

Applications is migrated at /applications and /applications/:applicationId/\*. It uses v1/applications CRUD and the existing canonical auth User entity for userId/user references, with v1/users?type=user searches and selected-account fallback reads. Feature scope identifiers are permission strings, not claims that their owning screens are migrated. Preserve localized English-required/Arabic-optional names, immutable clientName on edits, optional scope arrays, and unknown returned scopes.

Application forms use the reference header/tabs/BasicInfoTab layout, simple RTK API and applicationsSlice.js. Save only name/clientName/userId and scope feature/read/write/maxHourlyUsage, excluding API keys, populated users, nested scope metadata and timestamps. The old save handler dropped its editable maxHourlyUsage value; the migrated payload carries it through (including zero/null). No new positive/integer/minimum-scope validation is imposed. Known writable scopes (shipments and shipping-users) require read access; enforce this on user action/validation without modifying cached server data or resetting drafts during refetches.

API keys and integration details are view-only and use the configured API_BASE_URL, preserving /docs from the list dialog and /api-docs from the detail dialog. Reuse CopyableText. Do not create fake service URLs or send API keys in application writes. Deletion targets the selected detail ID, requires view/delete grants and confirmation; leave legacy-inactive table/bulk deletion unexposed. Staff view/create/update/delete grants apply, merchants cannot open the feature, and read-only fields include scope switches, hourly limits and account selection.

Redux dialog actions can freeze their nested payloads. Never pass live react-hook-form watch()/getValues() objects or their nested fields into an openDialog action. Pass only the primitive values the dialog needs, or explicitly clone editable data before dispatching. Application API-key dialogs use only the API-key string; opening/closing them must leave names/scopes editable.
