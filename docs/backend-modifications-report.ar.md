# تقرير backend المحدّث: التخزين ومراجعة شركات الشحن

التاريخ: 2026-11-08. هذا هو التقرير الحالي لتسليمه لفريق backend، ويحل محل طلب تعديل endpoint `/review` في التقرير السابق.

المشروع: `C:\Users\MAJD\Desktop\Node.Js Projects\shipping-express-backend`، الفرع `develop`.

**ملكية العمل:** لم يُعدل backend في هذه الدفعة. التنفيذ والنشر لفريقه حسب قرار صاحب المشروع. الواجهة عُدلت لتستخدم العقد الحالي لمراجعة الشركات؛ لا تطلبوا إعادة endpoint قديم أو شاشة مقارنة مستقلة.

## 1. التصحيح الأساسي وما يعمل بالفعل

المسار الصحيح في router وفي بيئة التطوير هو:

```text
POST /v1/shipments/review/companies
```

التهجئة هي `companies`. لا تستدعي الواجهة `/v1/shipments/review` في الإنشاء أو المرتجعات أو الحاسبة، ولا تحتاج قائمة شركات منفصلة قبل التسعير.

تحققت من استجابة API المنشور `https://api.v1.dev.e5hh6.ashamcoexpress.com` بطلب تسعير فقط:

- `suitableCompanies`: أعاد SMSA بسعر إجمالي 24 ومعه `quoteId` فعلي.
- `unsuitableCompanies`: أعاد DHL وAramex وأسباب `SENDER_CITY_NOT_SUPPORTED` و`RECEIVER_CITY_NOT_SUPPORTED` لعنوان الفحص.
- لم تُنشأ شحنة ولم تُخصم رسوم أو يُضف رصيد في هذا الفحص. قيمة 24 تصف هذه الاستجابة فقط.

**إذًا: إصدار quoteId وتقسيم الشركات متوفران أصلًا في endpoint الشركات. لا نحتاج تعديل `/review` لإرجاع quoteId، ولا نحتاج endpoint مقارنة جديدًا.** المطلوب هو استكمال التخزين والتحقق وربط البيانات داخل هذا المسار القائم.

## 2. التدفق الذي تنفذه الواجهة الآن

1. يختار المستخدم مصدر الشحنة أولًا: خارج المخزون أو مستودع ومنتجات وكميات.
2. إذا اختار المستودع، يُملأ المرسل من اسمه وبيانات pickup المحفوظة. المرسل غير قابل للتحرير يدويًا في هذا المسار.
3. يكمل المستلم والطرد والدفع ويضغط المتابعة.
4. تطلب الواجهة `/review/companies` تلقائيًا، قبل اختيار أي ناقل؛ تعرض أسعار الشركات المناسبة، وغير المناسبة مع الأسباب.
5. يختار المستخدم أحد العروض الجاهزة؛ تغيير الاختيار لا ينفذ طلب تسعير منفصلًا.
6. الإنشاء يرسل جسم التسعير نفسه مضافًا إليه `shippingCompanyId` المختار و`quoteId` الخاص به.
7. إذا حُفظت جهة اتصال جديدة وتغير senderId/receiverId، تجدد الواجهة العروض عبر endpoint الشركات نفسه، ثم تأخذ عرض الشركة المختارة فقط. إذا اختفت الشركة أو تغير الإجمالي تطلب مراجعة جديدة بدل تغيير السعر أو الناقل بصمت.

المسار الحالي يقبل مستلمًا واحدًا في كل طلب. للشحنة متعددة المستلمين، ترسل الواجهة طلبًا واحدًا لكل مستلم معلّق، وليس طلبًا لكل شركة. تعرض الشركة قابلة للاختيار فقط إذا كان لها عرض صالح لجميع المستلمين المعلّقين، وتجمع أسعارهم. تحفظ `quoteId` منفصلًا لكل مستلم، وتُظهر سبب الاستبعاد منسوبًا للمستلم المعني. لا نفترض وجود batch endpoint غير موثق.

## 3. عقد المراجعة والإنشاء

### طلب مراجعة الشركات

جسم الطلب مستقل عن الناقل: لا `shippingCompanyId` ولا `quoteId` ولا owner override. يحتوي البيانات الحالية للشحنة، ومنها IDs وعناوين الاتصال والوزن والمقاسات وCOD/coupon عند اختيارهما، وwarehouseId/products لمسار المخزون فقط.

```json
{
  "method": "local",
  "type": "box",
  "senderName": "Dispatch warehouse",
  "senderPhone": "+966-555123456",
  "senderCountryId": "country-id",
  "senderStateId": "state-id",
  "senderCityId": "city-id",
  "senderCountryName": "Saudi Arabia",
  "senderStateName": "Canonical region",
  "senderCityName": "Canonical city",
  "senderStreet": "Pickup street - العنوان الوطني: ABCD1234",
  "receiverName": "Receiver",
  "receiverPhone": "+966-555123457",
  "receiverCountryId": "country-id",
  "receiverStateId": "state-id",
  "receiverCityId": "city-id",
  "receiverStreet": "Delivery street - العنوان الوطني: RECV1234",
  "description": "Stored products",
  "weight": 1,
  "length": 10,
  "width": 10,
  "height": 10,
  "packagesCount": 1,
  "isCod": false,
  "warehouseId": "warehouse-id",
  "products": [{"warehouseProductId":"product-id","title":"Product","price":5,"quantity":2}]
}
```

المعرفات هنا placeholders؛ الطلب الفعلي يستخدم ObjectIds الحقيقية. الحقول الاختيارية والقيم النهائية تتبع validation الحالية. phones رئيسية فقط بصيغة dial-code + hyphen + national number.

### الاستجابة الحالية المطلوبة دون تغيير أسمائها

```json
{
  "suitableCompanies": [
    {
      "shippingCompany": {"id":"carrier-id","name":"Carrier","serviceName":"smsa","logoUrl":"https://example.test/logo.png"},
      "calculation": {"shippingCompanyPrice":24,"subtotal":24,"total":24},
      "quoteId": "server-issued-quote-id"
    }
  ],
  "unsuitableCompanies": [
    {
      "shippingCompany": {"id":"other-carrier-id","name":"Other carrier","serviceName":"other"},
      "reasons": [{"code":"RECEIVER_CITY_NOT_SUPPORTED","message":"Does not support the receiver city"}]
    }
  ]
}
```

بيانات shippingCompany الحالية مختصرة؛ الواجهة لا تختلق `hasState/isEnglish/shippingMethods/isAuthorizationRequired` ولا تستخدم غيابها كرفض لكل الشركات. يجب أن يكون تصنيف الخادم موثوقًا ويطبق هذه القواعد. إن أضفتم metadata اختيارية فأخبروا فريق الواجهة؛ لا تغيّروا أسماء المجموعتين أو موضع calculation/quoteId دون تنسيق.

### طلب الإنشاء

`POST /v1/shipments` بنفس بيانات المراجعة، مضافًا إليها فقط الناقل ومعرّف عرضه. تبقى الأسماء الجغرافية والـIDs في جسم الطلب canonical، ولا تستبدلها الواجهة بأسماء ناقل آخر بعد التسعير. بيانات الناقل الفعلية تؤخذ من providerInput الذي حُفظ بالخادم.

## 4. تعديلات backend المطلوبة للمخزون

### أ. حفظ pickup كاملًا

الفحص السابق على البيئة نفسها أثبت أن POST warehouse أعاد 201 لكنه أسقط pickup، وأن PATCH به أعاد 422 للمفتاح غير المعروف. يلزم دعم الحفظ والقراءة والرد بعد الحفظ في المسارات الحالية:

```json
{
  "name":"Warehouse name",
  "address":"Human-readable full address",
  "mapAddress":"https://www.google.com/maps?q=...",
  "information":"Warehouse information",
  "pickup":{
    "phone":"+966-555123456",
    "email":"warehouse@example.test",
    "countryId":"country-id",
    "stateId":"state-id",
    "cityId":"city-id",
    "street":"Pickup street",
    "nationalAddress":"ABCD1234",
    "zipCode":"12345"
  }
}
```

الهاتف والدولة والمنطقة والمدينة والشارع والعنوان الوطني مطلوبة لتهيئة الإرسال في الواجهة. email/ZIP اختياريان عمومًا؛ قواعد الناقل/الشحن الدولي قد تتطلب ZIP عند التسعير. تحققوا من وجود المراجع وترابطها. المستودعات القديمة يمكن قراءتها والتوريد إليها، لكن لا تُرسل شحنات منها قبل استكمال pickup. لا تُخمنوا عنوانًا من رابط الخريطة أو عنوان التاجر.

### ب. إدخال المخزون في review/companies نفسه

- يجب أن تحتفظ schema الخاصة بـreviewCompanies وcreate بـwarehouseId وproducts[].warehouseProductId وquantity؛ لا تُسقط أيًا منها أثناء validation.
- افحصوا الاشتراك الفعال للمستخدم الحالي، وملكية المنتج والمستودع، والكميات الصحيحة الموجبة والمتاحة، وعدم تكرار المنتج أو مزج مستودعات/منتجات خارجية بهذا الطلب.
- استخرجوا المرسل من المستودع، وعنوان الاستلام وبيانات المنتج وسعر القطعة من البيانات المحفوظة، لا من قيم يستطيع العميل تبديلها.
- داخل مراجعة كل شركة، طبقوا mappings وعنوان الاستلام الخاص بتلك الشركة على البيانات المعتمدة، ثم تحققوا من الملاءمة واحسبوا السعر واحفظوا quote.
- لا تستخدموا helper مصممًا لاستقبال shippingCompanyId واحد فقط قبل حلقة مقارنة الشركات دون تكييفه؛ طلب المستخدم هنا لا يحمل ناقلًا مختارًا بعد.
- احفظوا warehouseId في سجل الشحنة، ولا تنشئوا أو تعيدوا استخدام shipping-user خاص بالتاجر كمرسل للمستودع. يظل حفظ المستلم الجديد حسب التدفق الحالي.

### ج. ثبات البصمة وبيانات التنفيذ

المصدر الحالي يخزن `requestData` مستقلًا عن الناقل و`providerInput` بأسماء الناقل. احتفظوا بهذا الفصل أو بآلية مكافئة تضمن قبول جسم الطلب الصحيح دون إضعاف التحقق.

اختيار الناقل لا يغير جسم المراجعة؛ الإنشاء يحدد الناقل وquoteId فقط. الربط بالمستخدم والناقل ومدة الصلاحية وعدم الاستهلاك وتغير الكميات/العناوين/contact IDs يجب أن يظل فعالًا. أي تغيير في pickup بعد التسعير يجب أن يتطلب مراجعة جديدة، لا أن ينتج حجزًا من عنوان آخر بصمت. بيانات السجل والحجز الفعلية يجب أن تعكس المرسل المعتمد من الخادم، حتى لو حاول العميل تزوير snapshot.

أعيدوا رفض التحقق/التسعير المؤكد قبل queue.add بحالة 4xx مناسبة؛ 500 بعد POST قد يعني نتيجة غير مؤكدة، والواجهة لا تعيده تلقائيًا.

### د. التخصيص والنتيجة

فحص المخزون في التسعير لا يحجز كمية. worker يفحص الاشتراك والكمية مجددًا ويخصم ذريًا بشرط المنتج + المستخدم + المستودع + الكمية، داخل معاملة حفظ السجلات والتخصيص. خصم المحفظة وسجلاته لا يتكرر.

احتفظوا باستعادة الكمية مرة واحدة ورد الرسوم عند الفشل/رفض الناقل المؤكد حسب المنطق الحالي، وبـreconciliation عند نتيجة حجز غير معروفة. `201` message يعني قبول الصف؛ النجاح النهائي يتطلب رقم تتبع وlabel صالحين وخصم المخزون والمحفظة مرة واحدة. أي معرف مهمة/حالة جديد يُنسق مع الواجهة، ولا نفترض وجود endpoint غير موثق.

## 5. اكتمال تصنيف الشركات والتحقق من الأسعار

بفحص مصدر `review-shipment-companies.ts`، توجد بالفعل قواعد method/location mappings/Arabic addresses وفصل PRICING_FAILED. راجعوا أيضًا:

- صلاحية الحساب إذا كانت الشركة تتطلب authorization، وتوافق COD والكوبون. لا تُرجعوا شركة suitable ثم ترفضوها لاحقًا لقاعدة يمكن تحديدها أثناء المراجعة.
- أسماء الأشخاص إذا كان الناقل يتطلب الإنجليزية، وحدود الحقول والطرود والرمز البريدي والشروط الخاصة بالناقل.
- الوزن الحجمي: الفحص العام في المقارنة يستخدم 5000؛ الواجهة تستخدم 4000 لـAramex و5000 لغيره. طبقوا قاعدة الناقل الصحيحة داخل تصنيفه بدل إرجاع عرض غير قابل للتنفيذ، واحتفظوا بالشركات الأخرى المناسبة.
- السعر يجب أن يكون رقمًا finite وغير سالب، مع بقاء الصفر صالحًا. لا تحفظوا quote بقيمة NaN/Infinity/سعر غير صالح؛ أعيدوا سببًا واضحًا.
- العرض الخاص بالتاجر وCOD/coupon والضريبة/الإجمالي يجب أن تُحسب من الخادم وتبقى نفس calculation عند تنفيذ الطلب المقبول.
- **فاصل العنوان الوطني:** الجسم canonical يتضمن حاليًا ` - العنوان الوطني: `. لا تعتبروا هذا الوصف الذي يضيفه النظام عنوانًا عربيًا كتبه المستخدم وتستبعدوا بسببه كل ناقل إنجليزي. افصلوا/طبّعوا العنوان الوطني ثم طبقوا قواعد اللغة وصيغة street/shortCode الخاصة بالناقل في providerInput، مع إبقاء البصمة مستقرة. لا تطلبوا من الواجهة تعديل الجسم حسب الشركة قبل اختيارها.
- الأسماء العامة ليست بديلًا عن mappings. لا تختاروا mapping لناقل آخر ولا تعيدوا بيانات تغطية ناقصة كعرض صالح.
- احتفظوا بالأسباب كـcode/message لكل شركة، وبالأسباب غير المعروفة مستقبلًا بدل إسقاطها. الواجهة تترجم الأكواد الحالية وتعرض message للأكواد الإضافية.

هذه نقاط مراجعة مصدر وعقد، وليست كلها أعطال مثبتة بحجز حي. النتيجة المؤكدة في الفحص الحالي هي أن المسار الصحيح يعمل ويصدر quoteId؛ حجز المخزون الكامل لم يُثبت بعد.

## 6. ما يظل مطلوبًا من التقرير السابق

- خطط التخزين والاشتراك والتوريد الأساسي عملت: pending/approved لا يضيفان كمية، وreceived يضيفها مرة واحدة. حافظوا على أنواع التخزين المسموحة من الباقة وهوية المخزون (مستخدم/مستودع/نوع/SKU أو اسم).
- اختبروا استلام طلبين متزامنين لمنتج جديد مطابق؛ index الحالي غير unique، فلا تفترضوا أن upsert وحده يمنع كل الازدواج. عالجوا السباق بطريقة تناسب البيانات الحالية دون قيد فريد أعمى.
- اختبروا queue replay والفشل بين إضافة المهمة وتحديث consumedAt، ومنع تكرار الحجز/الخصم.
- استخدموا أنواع ObjectId/مراجع domain الصحيحة، وأعلنوا virtual mappings في ICity/IState إذا استُخدمت؛ لا تخفوا أخطاء بناء pickup باستخدام any.
- راجعوا package-lock/npm ci تحت Node 20. في الفحص السابق احتاج lockfile إلى مزامنة 21 مدخلًا من AWS/Smithy دون تغيير package.json، ثم نجح بناء نسخة معزولة. الفريق يعيد التحقق من نسخته الحالية بعد إلغاء التعديلات المحلية.
- لا تُرجعوا أكواد تحقق أو tokens في user populated الخاص بـshipping-users؛ الفحص السابق وجد emailCode داخل هذه population. استخدموا projection آمنًا مع الحفاظ على بيانات المالك اللازمة والـIDs والعدادات والجغرافيا.
- لا sender prefix أو هاتف ثانٍ في الطلبات الجديدة، ولا isCommercial أو acceptExtraWeightTerms من الواجهة. products للشحنة الخارجية محذوفة؛ المخزون وحده يرسل منتجاته. لا تعيدوا ميزات المتجر أو شاشات المقارنة المستقلة المحذوفة.

## 8. معيار قبول بعد التنفيذ والنشر

1. إنشاء/تعديل/قراءة مستودع pickup كامل دون إسقاط حقول، مع رفض مراجع جغرافية غير مترابطة.
2. اشتراك فعال، توريد متعدد المنتجات، نوع خارج الباقة مرفوض، عدم ظهور كمية قبل الاستلام، وجمع الكميات مرة واحدة بعده.
3. مراجعة الشركات بلا shippingCompanyId: استجابة واحدة لكل مستلم تضم مجموعتي النتائج وأسعارًا وquoteIds صالحة وأسبابًا لكل مرفوض.
4. التحقق من المخزون والمرسل الحقيقي داخل المراجعة، وتغطية لغة/COD/coupon/auth/وزن الناقل.
5. اختيار شركة من العروض ثم إنشاء بنفس جسم المراجعة مع معرفها وquoteId؛ لا يحدث فشل بصمة بسبب اختلاف أسماء canonical وأسماء الناقل.
6. مستلم جديد: حفظ ID ثم مراجعة شركات جديدة، واختيار نفس الشركة مع نفس الإجمالي أو طلب تأكيد جديد عند التغير.
7. رفض quote منتهي/مستهلك/لمستخدم أو شركة أخرى، ورفض تغيير الكمية/المستلم/المستودع دون مراجعة.
8. شحنة sandbox واحدة حتى trackingNumber وlabel فعليين، مع خصم المخزون والمحفظة مرة واحدة. لا يكتفى بـ201.
9. اختبار عدة مستلمين، فشل مراجعة أحدهم، نجاح جزئي ثم retry، التزامن، الرفض المؤكد والنتيجة المجهولة دون تكرار.
10. التأكد من بقاء الشحن الخارجي والمرتجعات والحاسبة سليمًا عبر endpoint الشركات نفسه.

## 9. نتيجة تنفيذ الواجهة والتحقق

اكتمل تعديل API والأنواع وتدفق الإنشاء والمرتجعات والحاسبة والعرض المحلي. الواجهة تعرض مجموعتي الشركات تلقائيًا، وتحافظ على COD والكوبون والعناوين ونتائج المستلمين، وتجدد عرض الشركة نفسها عند تغير معرف جهة الاتصال. لم يُعدّل أي ملف backend في هذه الدفعة.

- نجح فحص TypeScript للتطبيق وبناء production وdemo.
- نجحت 40 حالة regression للشحن و28 للتخزين، وقبلت schemas المحلية ستة payloads.

## نص جاهز لإرساله إلى Codex لدى فريق backend

> نفذ متطلبات هذا التقرير في مشروع backend وفق تعليماته. التدفق المعتمد هو POST v1/shipments/review/companies فقط لمراجعة الناقلين؛ endpoint موجود ويعيد suitableCompanies/calculation/quoteId وunsuitableCompanies/reasons فعلًا، فلا تضف endpoint جديدًا ولا تعدل review المنفرد من أجل الواجهة. استكمل حفظ warehouse.pickup وربط المخزون والمرسل المعتمد من الخادم داخل مقارنة كل شركة، واحتفظ بمعرفات warehouse/products والكميات في validation والبصمة. احفظ جسم المراجعة المستقل عن الناقل منفصلًا عن providerInput الخاص به، وتحقق عند الإنشاء من quoteId/المستخدم/الشركة/الصلاحية/التغيرات دون إعادة تسعير مقبول بصمت. راجع COD/coupon/auth/language/volumetric rules وفاصل العنوان الوطني، والتخصيص الذري والتعويض وqueue replay، وأصلح أنواع MongoDB/virtuals وCI lockfile وprojection shipping-users التي تسرب أكواد التحقق. اختبر السيناريو كاملًا حتى حجز sandbox حقيقي وتتبع وبوليصة ومخزون ومحفظة صحيحين، وأرسل أمثلة الاستجابات النهائية والنسخة المنشورة لفريق الواجهة. التعديلات المحلية القديمة قد يُلغيها صاحب المشروع فلا تعتمد على بقائها، ولا تنشر قبل اتباع آلية موافقة الفريق.
